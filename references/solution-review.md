# 多方案评审标准（solution-review）

目标不是找“最正确的文档”或“最先进的方案”，而是：**以当前真实需求为圆心、以真实代码与证据为边界，得到当前条件下幸存下来的、可执行、可解释的方案。** 由规划者执行，结果落成决策记录（DEC）。

## 1. 何时需要生成备选方案
**需要**（任一）：
- 会改变核心架构、数据模型、公共契约语义、权限/安全边界、关键依赖或成本结构；
- 不可逆或高回滚成本（数据迁移、删除、对外发布的接口）；
- 多份资料/多个助手对同一问题给出不同主张；
- 实测推翻了原假设（如瓶颈不在预期位置）；
- 预计影响 ≥ 3 张任务卡或跨 ≥ 2 个所有权区域。

**不需要**：命名、样式、单文件内实现细节、已有 `DECIDED` 决策覆盖的问题、可在一张卡内低成本回退的选择。这些由执行助手按卡面处理，必要时记一条 NON_BLOCKING 假设。

## 2. 分析深度分级（按风险，不按形式）
| 级 | 触发 | 要做的 |
|---|---|---|
| L1 记录 | 一般主张 | 主张、类型、来源、关联需求、证据 |
| L2 争议 | 多方主张不同 / 证据矛盾 / 设计与代码不一致 / 不确定性高 | + 优点、代价、失效条件、隐含前提、需求匹配、反证 |
| L3 决策 | §1 的“需要”情形 | + 5W1H、苏格拉底追问、双向钢人、反例、反事实、可逆性（见 `planner-protocol.md` §10） |
| L4 高风险 | 不可逆、数据迁移、安全边界、生产部署、大额长期成本 | + 实际代码/配置核查、实验或基准、失败模式、回滚方案。需副作用的验证排成探索卡交执行/测试助手 |

禁止对所有细节机械执行 L3；也禁止对 L3 问题只给一句“建议采用 A”。

## 3. 候选方案的生成规则
- 至少评估**两条真实可行**路径。客观上只有一条满足硬约束时，写：`唯一可行方案 + 至少一条真实评估并被排除的路径 + 排除理由`。**禁止为凑数伪造方案。**
- “维持现状 / 不做”是合法候选，常常应该列入。
- 方案可以是组合：A 的一部分 + B 的一部分 + 重新设计的部分；也允许结论是“参考资料都不适合，需重建”。
- 每个方案写清：做法一句话、改动范围（模块/文件/契约）、依赖前提、可逆性。

## 4. 证据要求
每个支撑评分的论断附证据，用技能统一的证据链表示：
- **E1 来源**：需求/决策编号、用户本轮要求。
- **E2 实现**：文件路径 + 符号/行号 + 提交号（现状以代码为准）。
- **E3 验证**：实际命令 + 结果，或实验/基准（同环境、交错 A/B、样本数）。
- 外部资料（官方文档、RFC）只证明“技术本身支持什么”，不证明“本项目需要什么”。

**证据纪律**：
```text
[ ] 区分 FACT / CLAIM（某文档认为）/ INFERENCE / ASSUMPTION，不把“文档提出 X”写成“项目应该 X”
[ ] 独立性检查：A 引 B、C 也引 B ⇒ 只算一个来源（伪多源共识）
[ ] 负证据只写 NOT_FOUND（扫描范围内未找到）；只有资料明确说不支持才写 NOT_SUPPORTED
[ ] 历史 AI 产物（旧报告、旧总结）只是线索，不因“之前 AI 说过”升级为事实
[ ] 用户有权改变目标，但用户的话不能把未验证的技术事实变成已验证
[ ] 没有数据的指标不做伪精确量化，标【指标缺失】
```

**冲突先分类再处理**：事实冲突（去核实）/ 方案冲突（本流程比较）/ 目标冲突（交用户）/ 阶段冲突（旧文档 vs 新文档，通常不是真冲突）/ 假设冲突（找出分歧前提）/ 概念冲突（同词异义，写 glossary）/ 权威冲突（当前要求覆盖旧约束时须明说“将覆盖此前约束”及后果）。

## 5. 评分维度与默认权重
**第 0 步：硬约束过滤**。违反任何 MUST、MUST NOT、已 DECIDED 决策、AGENTS.md 硬边界、安全底线的方案直接淘汰（除非本次评审就是要推翻该决策，此时走用户裁决）。过滤后不再给它打分。

**评分**：每维 0–3 整数分（0 不满足 / 1 勉强 / 2 满足 / 3 明显优于其他），**每个分数必须附一句证据或理由**，无证据的维度记 `?` 不计分并列入未决。

| 维度 | 默认权重 | 看什么 |
|---|---|---|
| 需求匹配 | 30% | 覆盖多少 MUST/SHOULD；是否解决真实问题而非技术偏好 |
| 证据强度 | 15% | 支撑论断的验证程度（E3 > E2 > E1 > 推断） |
| 实施成本与复杂度 | 15% | 改动面、新增抽象/依赖、工期；越小分越高 |
| 风险与可逆性 | 15% | 失败影响面、回滚成本、对数据/安全的影响 |
| 与现状契合 | 10% | 复用现有代码与契约的程度、迁移量 |
| 可验证性 | 10% | 能否用定向测试/阶段体检判定成功 |
| 演进余地 | 5% | 已知的下一步需求下是否需推翻重建（只算有证据的“下一步”，不为想象的未来加分） |

- 权重可按项目调整，但调整本身要写进 DEC（例如对性能项目提高“证据强度”）。
- 分数是**辅助排序**，不是裁决：总分差 < 10% 视为持平，由“关键分歧点”决定；出现单维 0 分要单独说明是否可接受。
- 不得用专家名望、“行业惯例”“更先进”给任何维度加分。

## 6. 攻击幸存者（L3/L4 必做，写简短结论即可）
```text
Q1 这个选择最可能错在哪？          Q2 它最依赖哪个前提？前提不成立会怎样？
Q3 什么证据能直接推翻它？          Q4 是否把技术偏好当成了需求？
Q5 是否在解决一个并不存在的问题？  Q6 是否因为某文档写得更详细就提高了权重？
```
- **双向钢人**：分别用最强版本论证首选和次选为何正确，不得故意弱化对方。
- **反例**：找至少一个能显著削弱结论的反例 → 成立吗？成立后方案还能保留吗？需加什么边界？
- **压力测试**（选相关项）：核心需求变化 / 关键组件失效 / 规模变化 / 更换模型、Provider、数据库、部署环境 —— 是否需要推翻重建？

## 7. 反模式（发现即退回重做）
1. 未建需求基线就用文档观点定义目标。
2. 把历史文档与当前文档机械平权，或把阶段差异当方案冲突。
3. 伪造候选方案凑数；只批评别的方案、不做双向钢人；只找正面证据不找反证。
4. 为形式上的 SOLID/DRY 或“先进”引入当前需求用不到的抽象、依赖、目录、表。
5. 无基线就提出性能“优化”；无数据给出精确指标。
6. 遇 BLOCKING 擅自假设；遇 NON_BLOCKING 无谓停摆。
7. 只给结论，不展示被排除的路径及理由。
8. 输出“绝对正确”“一定成功”“100% 置信”。
9. 把模糊回复（“好的”“嗯”“继续看看”）当成执行授权。
10. 评审过程顺手改业务代码（评审阶段只读，验证需要副作用时排成任务卡）。

## 8. 选定与记录（DEC）
用技能的决策模板（`templates/decision.md`）写入 config 的 `decision_dir`，并登记到**唯一**决策登记册。L3/L4 决策的正文至少包含：
```text
问题          当前到底要决定什么
当前条件      相关需求、约束、快照（commit）
候选与评分    每个方案一句话 + 评分表（含理由）；被硬约束淘汰的写淘汰原因
关键分歧      分歧真正来自哪个前提/目标
决定          采用什么（可以是组合）
理由与证据    E1/E2/E3
被放弃方案    及放弃原因
前提与边界    在什么条件下成立；明确不适用的场景
未解决风险    及缓解或后续卡
可逆性        REVERSIBLE / PARTIALLY_REVERSIBLE / IRREVERSIBLE
重新评估触发  如“Provider 数 > 1”“P95 超过阈值”“REQ-x 变化”
裁决人        planner（授权范围内）或 user；影响的任务 ID（applies_to）
```
- 存在 BLOCKING 时，记录为条件决策：条件方案 A/B + 共同部分 + 分叉点 + 待裁决变量，状态 `OPEN`，只阻塞受影响的卡。
- 推翻旧决策：新 DEC + `supersedes`，旧 DEC 置 `SUPERSEDED`，不改旧文件结论。
- 决定后由规划者同步：受影响任务卡（来源、验收、依赖）、契约（若变）、`plan_version`。
- 给用户的汇报用大白话：选了什么、为什么、放弃了什么、还有什么风险、需要你拍板什么。

## 9. 停止条件
满足以下全部即停止评审、进入记录：
```text
[ ] 硬约束过滤已完成，剩余候选都有逐维评分与理由
[ ] 首选方案经过 §6 攻击后仍成立，或已加边界条件使其成立
[ ] 再做一轮调查/实验预计不会改变排序（追加证据只在可能改变结论时才做）
[ ] 未决项都已分为 BLOCKING（交裁决）或 NON_BLOCKING（记假设+回退条件）
```
**提前停止**：只剩一个可行方案且已写明排除理由；或问题降级为可逆的低影响选择（转为普通实现细节，记一行假设）。
**升级**：两轮评审仍无法收敛、或分歧来自目标/范围/安全/成本承诺 → 交用户裁决，附推荐项和各方代价。
