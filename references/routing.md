# 会话启动路由与红旗表（v0.6.0，服务信条三“卡住就说”与信条一“只信证据”）

借鉴来源：obra/superpowers `using-superpowers`。它要求在任何回答（包括澄清提问）之前先检查技能，有 1% 可能适用就加载，并用红旗表逐条驳斥常见借口。本 Skill 只借这套纪律，路由目标仍以本 Skill 的模式为准。

## 1. 什么时候路由

- 会话开始、收到新意图、模式切换时：先路由，再回答或动手。
- 由 `pd.mjs prompt/next` 生成的执行提示词首行写着“已路由，勿再路由”，执行助手直接干活。
- 小需求快速通道同样适用，只是路由结果更轻，不跳过路由这一步。

## 2. 路由三问（10 秒内答完）

1. **哪个模式？** 对照 SKILL.md §2 的触发词；拿不准时，选风险更低的只读模式，并告诉用户。
2. **要读什么？** 只读这一模式必需的文件：任务卡、引用的决策和契约、`pd.mjs status`。不通读全部文档；大于 32 KB 的文档先看目录再按节读。
3. **借哪个外部 Skill？** 查下表，装了就用，没装按内置步骤走。

| 阶段 / 任务类型 | 优先调用（若已安装） | 本 Skill 的约束 |
|---|---|---|
| DISCUSS | superpowers `brainstorming` | 一次一问；结论当场 RECORD |
| RECORD / 需求变更 | OpenSpec 变更提案（ADDED/MODIFIED/REMOVED + Given/When/Then） | 编号用本 Skill 的 DEC/任务 ID |
| PLAN | superpowers `writing-plans`（签名 + 路径 + 测试断言，不写代码体）；planning-with-files | 规划落盘前做一轮 builder check（见 planner-protocol） |
| EXECUTE 通用 | superpowers `executing-plans`（连续执行，不在卡间停等）、`test-driven-development`、`systematic-debugging` | 只跑定向测试；偏离写裁决 |
| EXECUTE 前端/UI | `frontend-design`、`ui-ux-pro-max`、`web-design-guidelines` | 体检含 tsc 和 build |
| VALIDATE / PHASE_REVIEW | `verification-before-completion`、code review | 先合规后质量；问题须带反例 |

## 3. 规划者红旗表

| 借口 | 反驳 |
|---|---|
| “这个执行助手应该看得懂” | 做执行者测试：只给局部上下文，能不追问干完吗？ |
| “测试路径大概在允许范围里” | 逐卡核对测试路径 ⊆ 允许路径，有重叠就是规划缺陷 |
| “这张卡细节执行时再定” | 可以，但目标、依赖、验收现在必须写清，步骤标 REFINE_BEFORE_EXECUTION |
| “先发出去，有问题再改” | 已下发卡改动要 SUPERSEDED + 影响清单，代价远高于现在核对 |
| “这个 owner 一会儿就开工” | 看执行日志：就绪后有没有事件？没有就是停滞，第一行报 |
| “用户之前好像说过” | 查决策登记册；查不到就是没说过 |

## 4. 执行者红旗表

| 借口 | 反驳 |
|---|---|
| “应该可以了”“看起来对” | 没有本轮命令输出就不算完成 |
| “顺手把旁边也修了” | 允许路径之外一律不动，登记 D-EXEC 交给归属者 |
| “再试一次就好” | 同一卡失败两次就停手，写出共同前提后上报或标 BLOCKED |
| “这点小取舍先不记” | 不记就是暗箱决策，写一行裁决再继续 |
| “跑一下全量更放心” | 执行者只跑定向测试，全量是测试助手的事 |
| “卡面和代码对不上，我按理解改” | 先登记现象、证据、取舍和回退方法，再做最小可逆改动 |
| “先等规划者回复” | 能自裁的写裁决继续；只有四类必须停：不可逆、安全敏感、外部副作用、计划根本错误 |
| “测试输出太长，贴前面就行” | 输出落文件，只回通过/失败计数、前几个失败和路径 |
