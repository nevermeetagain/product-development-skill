# 规划者协议（planner-protocol）

适用：`PLAN`、`REPLAN`、执行前细化、裁决。产出不是“好看的文档”，而是一组**机器可执行的指令**：会被拆给多个互不通信的执行助手并行使用，它们唯一共享的是契约和任务卡。

> **唯一质量判据**：一个只有局部上下文的执行助手，拿到任务卡和它引用的文件，能否**不追问、不猜测**地干完并自证完成？不能 → 规划不合格。

## 0. 硬约束
- 规划阶段只写规划产物（§9 清单），不改业务代码、测试代码、依赖、配置。
- 缺关键事实 → 标 `BLOCKING`，不编造；宁可少，不可假（不凑方案、不凑任务）。
- 每个结论可反向追溯到需求/决策（E1）或真实代码（E2）。不用“最佳实践/行业惯例/专家说”当论据。
- 不写“100%”“一定成功”“绝对正确”；用“查了什么、哪些有证据、哪些未验证”表达。
- 需求冲突或缺失必须显式列出，不静默替用户决定。

## 1. 事实基线（不可跳过）
**1.1 读规则**：AGENTS.md / CLAUDE.md（依赖方向、所有权、禁止项、完成定义是硬边界）→ README → config.json 指向的决策登记册、任务索引、测试台账 → 治理文档（project-map / glossary，若有）。

**1.2 读需求**：全量检索，不只看文件名靠前的几个。覆盖功能、非功能、约束、inbox 原始需求。

**1.3 核对代码现实**（文档 ≠ 实现）：
```text
[ ] 实际目录结构   [ ] 实际依赖（lockfile）   [ ] 已实现模块/接口
[ ] 实际测试命令（package.json scripts / Makefile / CI）   [ ] git status + 最近提交
```
文档与代码不一致时，**现状以代码为准**，并逐条记录差异：`MATCH / PARTIAL / DIVERGED / MISSING / UNKNOWN`。执行助手的自述不算完成证明。

**1.4 快照**（钉住规划所依据的状态，写入 master_plan 头部）：
```yaml
snapshot: { date: <绝对日期>, branch: <>, commit: <HEAD>, dirty: <bool>,
            plan_version: PLAN-R<n>, requirement_sources: [<路径@修改时间>], test_cmd: <实际可运行命令> }
```
**1.5 输出事实基线**：已确认（附证据）/ 仅文档声称（标来源）/ 文档-代码差异 / 读取失败的部分（必须列出）。
负证据只能写 `NOT_FOUND`（扫过的范围内没找到），不得写成“项目不支持”。

## 2. 需求基线复核
需求即使已由人整理，也要独立复核。
1. **复述**：一段话说清核心问题、用户是谁、管理端是谁、系统边界。
2. **分级**：`MUST / SHOULD / COULD / MUST NOT`（MUST NOT 框定范围，同等重要）。
3. **可验证改写**：每条 MUST 改写成一句可判定的话（谁、在什么条件下、观察到什么）。改写不了 → 是愿望不是需求 → 标“待澄清”。
4. **冲突检查**：
```text
[ ] MUST 之间矛盾？   [ ] MUST 与 MUST NOT 冲突？
[ ] 非功能（性能/成本/工期）与功能复杂度兼容？   [ ] 与技术约束（端口/部署/现有栈）冲突？
[ ] 是阶段差异（旧文档 vs 新文档）而非真冲突？——先排除这一种
```
5. **未知登记册**：每项判 `BLOCKING`（会让规划根本分叉 → 人裁决）或 `NON_BLOCKING`（记假设 + 依据 + 回退条件，写进相关任务卡，继续）。
   BLOCKING 不擅自假设，也不让整个规划停摆，必须给出：
```text
条件方案 A | 条件方案 B | 两者共同部分（可先做）| 分叉点 | 需裁决的变量与裁决人
```
6. **补全隐含项**：隐含要求、未说明的前置条件、歧义表述、失败边界、模块间依赖。
7. **非功能指标**：能量化的转成指标；资料没给数字就标 `【指标缺失】`，交用户定，**不自己编数字**。

## 2.5 项目结构（STRUCTURE）
需求复核后、契约冻结前，以架构师身份按 `project-structure.md` 产出 `docs/architecture/project-structure.md`（树 + 所有权 + 依赖规则 + 16 个核心维度 + 安全、测试 2 个横切项的决定）。§7 所有权矩阵与卡面允许/禁止路径直接引用它；骨架与守卫配置并入 §4 首刀。

## 3. 契约冻结（并行开发的唯一中间语言）
按项目实际涉及的面选择，不涉及的写 `N/A + 理由`：

| 契约 | 必含 |
|---|---|
| API | 路径、方法、请求/响应 Schema、分页、幂等、鉴权 |
| Errors | 错误码枚举、HTTP 映射、错误体结构、前端展示方式 |
| Identity | 用户 ID 形态、角色枚举、session/JWT 声明、管理端与用户端权限边界 |
| Resources | 文件/图片 URL 规则、上传鉴权、访问控制、生命周期 |
| Events | 事件名、载荷、触发时机、幂等键（无异步则 N/A） |
| UX States | 核心界面的空/加载/错误/无权限/成功态 |
| Data | 实体与关系、字段（类型/可空/默认/约束）、索引、软删除、**迁移版本号顺序** |

**形式要求**：指定**唯一源**（OpenAPI / JSON Schema / zod / 语言原生类型 选一），其余从它生成，禁止多源；机器可校验；字段命名、时间格式、金额单位、枚举全项目统一；同一概念一个名字（写 glossary）。

**自检（任一为否 → 不完备 → 依赖它的任务不得并行开工）**：
```text
[ ] 前端只凭契约能写完调用层，不用问后端？
[ ] 后端只凭契约能实现接口，不用问前端要字段？
[ ] 数据端只凭契约能设计表结构？
[ ] 错误码覆盖所有已知失败路径？
[ ] 越权路径（尤其管理端）在 Identity 中被明确禁止？
```
契约冻结后变更 = 新决策（DEC）+ 受影响任务清单，由规划者裁决。

## 4. 垂直切片 + 步行骨架
- 切片 = **端到端可演示的行为**（UI+API+DB），不按技术层切（不要“前端组/后端组/数据组最后融合”）。
- 质量：每刀结束用户主路径多一个可演示行为；半天到两天可演示；< 2 小时的改动并入相邻刀；每刀可独立验收；切片间靠契约解耦，不靠互相等。
- **第一刀 = 步行骨架**：最小闭环（健康检查 + 一个鉴权过的写接口 + 一张表 + 一次迁移 + 前端打到真实 API 的页面 + 统一错误响应）。已有项目若骨架已存在，写明证据并跳过。
- 排序：先解锁依赖多的，先做不确定性高的（尽早暴露风险）；标出可并行/必须串行。

## 5. 三级分解
```text
Work Package（交付一大块什么）→ Atomic Task（最小可独立验证的交付）→ Step（怎么做）
```
Task 回答“交付什么”，Step 回答“怎么做”，不混写。
- 粒度过大信号：验收 > 6 条 / 跨 ≥ 3 个模块 / 预估 > 2 天 → 拆。
- 粒度过小信号：< 2 小时 / 验收只有“能跑” → 合并。
- 一张卡不应还能拆成多个彼此独立的交付结果。

## 6. 任务卡必填字段
索引条目（task-index.json）与卡面（tasks/<ID>.md）各司其职，字段定义见 `planning-and-task-contract.md`。规划者必须保证以下内容齐全：

| 字段 | 要求 |
|---|---|
| id / phase / role | 稳定 ID，下发后不改号不复用 |
| 来源 E1 | REQ / DEC / 方案编号；无来源的卡不得存在 |
| 目标 | 一句可观察、可验证的话 |
| 输入 | 引用的文档、契约名（具体到接口/DTO）、前置任务、前置状态（如“迁移 003 已合并”） |
| 输出 | 新增/修改的文件路径（到目录或文件） |
| 允许 / 禁止修改 | 路径模式；默认禁止：契约源、迁移目录、他人所有权路径 |
| Steps | 可执行动作；不确定时标 `REFINE_BEFORE_EXECUTION` 并写清不变量和分支触发条件 |
| 验收 | `command / measure / manual` 三选一，可判定；人工项写清判断标准与证据位置 |
| 定向测试 | 执行助手只跑这些（可复制执行的命令） |
| 依赖 / 阻塞条件 | depends_on、blocks；“遇到什么就停下上报” |
| 风险 / 停止条件 | 探索与性能类必须有继续条件和停止条件 |
| 规模与升级条件 | 小/中/大；什么情况必须升级给规划者（如连续 2 次验收失败） |

**熔断**：同一卡连续 2 次验收失败 → 停止改代码，改为重写卡面 / 拆卡 / 升级 / 标 BLOCKED。禁止换个提示词硬撞第 3 次。

## 7. 所有权、依赖与并行
**所有权**按仓库路径划分（不是按“前端/后端”产品）。输出一张 `角色或助手 × 路径` 矩阵，**重叠即规划缺陷，必须消除**。契约源与守卫配置（CI、边界检查）不与实现并行修改。跨所有权需求 → BLOCKED + 上报，不“先写了再说”。

**并行判定是机械规则，不是感觉**：
```text
可并行 ⟺ 无共享可变状态 ∧ 依赖的契约已冻结 ∧ 文件所有权不相交 ∧ 不共用迁移版本号
```
任一不满足 → 串行。每条并行结论附上满足了哪几条。并行还要**有收益**才并行（同时写入的助手建议 ≤ 3）。

**DAG 输出**：可并行组 / 串行链 / 关键路径 / 环检测结果（不得有环）。
**迁移串行**：同一张表、同一迁移目录的改动按 §3 定好的版本号顺序串行。

## 8. 阶段收口、指标与完成口径
- 每个阶段末尾排一张 `role: tester` 的阶段体检卡（只覆盖本阶段改到的模块，前端含 tsc + build）；全部完成后排一张最终回归卡。**不给每张卡加门禁或全量回归。**
- 性能目标：先定义 3–5 个用户可感操作及可测指标，证明“这个数降了用户能感到”；**没有基线数字不排优化卡**（基线可由第一张探索卡实测得到）。
- 完成口径（与 SKILL.md 一致）：`DONE` = 所有权内 diff 符合卡面 + 定向测试通过 + 已提交 + 留痕；`VERIFIED` = 测试助手在台账有 PASS。验收标准由规划者定、执行助手实现、测试助手判定，防止自证循环。

## 9. 落盘与自检
**只写这些**（实际路径以 config.json `paths` 为准）：master_plan、task_index、task_cards、decision_index/decision_dir、契约唯一源目录（若本次规划冻结契约）、glossary（若有）、project_structure 结构文档。业务代码、测试代码、配置一律不写。

**输出顺序**（某节无内容写“无 + 原因”）：
```text
1 快照  2 事实基线（含差异清单）  3 需求复核（分级/冲突/未知/隐含）  4 契约与数据基线
5 切片与排序理由  6 任务卡全集  7 DAG  8 所有权矩阵  9 风险/未决/待裁决（分开列）
10 落盘清单（路径+一句用途）  11 自检结果  12 前提与局限  13 建议第一刀与启动顺序
```
**自检（任一未过 → 修正后再输出）**：
```text
需求  [ ] 每条 MUST 可验证或已标待澄清  [ ] 冲突全部列出  [ ] BLOCKING 有条件方案 A/B
契约  [ ] 涉及的契约齐全且唯一源  [ ] 三方只凭契约可开工  [ ] 越权路径已禁止
任务  [ ] 垂直切片、首刀骨架  [ ] 每卡字段齐全、有验证命令、有允许/禁止路径、可追溯到 E1
并行  [ ] DAG 无环  [ ] 并行结论附机械依据  [ ] 关键路径标出  [ ] 所有权无重叠
测试  [ ] 每阶段有 tester 体检卡  [ ] 有最终回归卡  [ ] 无逐卡门禁
纪律  [ ] 未改业务代码  [ ] 无无证据绝对结论  [ ] 未验证项已标注  [ ] pd.mjs health 通过
```

## 10. 深度推理协议（只用于高影响决策）
**何时用**（任一即触发）：核心架构、数据模型、公共契约语义、权限/安全边界、不可逆或数据迁移、关键技术选型、成本结构、实测推翻了原假设。普通实现细节、样式、命名**不用**——问题风险越高分析越深，禁止为显得深刻而机械套用。

**三轮，写进决策记录（DEC）而不是聊天**：
1. **发散 5W1H**：What（事实/现象，哪些已证实、哪些只是声称）· Why（直接原因 vs 根因；只改表面会留下什么）· Where/When（适用边界、时序、哪些步骤必须在前、哪些不在范围）· Who（谁受益、谁承担成本与风险、谁有决策权）· How（实现路径、依赖、如何验证）· What if（配置缺失、依赖不可用、字段变化、规模变化、前提不成立时结论怎样）。
2. **收敛：苏格拉底追问 + 双向钢人**。对每个关键结论至少问：
```text
凭什么？证据来自最新代码吗？最可能错在哪？最依赖哪个前提，前提不成立会怎样？
什么证据能直接推翻它？是否把技术偏好当需求？是否在解决不存在的问题？最强反例是什么？
```
   再分别用**最强版本**论证“为什么成立”和“为什么不成立”（不得故意弱化对方），然后写明：哪些反对意见已被证据排除、哪些仍成立、哪些转为后续任务。
3. **重构**：只基于幸存论点下结论，并附：前提、局限、未验证项、可逆性（可逆/部分可逆/不可逆）、重新评估触发条件。

结论状态用：`已确认 / 部分确认 / 证据不足 / 待其他角色完成 / 需返工 / 暂不执行`。多方案比较的打分与记录见 `solution-review.md`。
